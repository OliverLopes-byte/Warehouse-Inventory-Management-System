How to use this guide

Learn the story of one item moving through the warehouse. The rest of the system becomes easier to explain once that story makes sense.

  1. Understand what the system is for and who uses it.
  2. Follow the example flow: set up a product, order it, receive it, store it, issue or transfer it, then report on it.
  3. Review the role rules, database records, and how stock stays correct.

One-sentence summary: This project is a warehouse inventory API that records what was ordered, received, moved, counted, and issued, while keeping a current stock balance and a permanent movement history.

01 · Big picture

What problem does it solve?

A warehouse needs to know what products it has, where goods came from, what has been sent out, and how much remains. A spreadsheet can be overwritten or become inconsistent. This system stores each business record in a database and provides controlled API operations for changing and reading those records.

What it can do

  • Maintain warehouses, bins, products, categories, units, suppliers, and user accounts.
  • Create purchase orders and receive goods against those orders.
  • Issue stock, transfer it between warehouses, and correct counts with a reason.
  • Show current balances and the history behind those balances.
  • Warn managers about low stock and recorded expiry dates.
  • Give administrators warehouse valuation and product movement analysis.

What the user sees

The project is a backend REST API. Its included Swagger UI is a browser-based page for reading endpoint descriptions and trying API requests. There is no separate custom inventory dashboard in this repository.

Important boundaries

  • Stock balance is tracked for a product in a warehouse. It is not a separate quantity for each bin.
  • A receipt line names a bin, and the system saves that bin on the receipt. The aggregate balance model is still warehouse/product, not warehouse/bin/product.
  • Expiry is stored on the warehouse/product balance row; this is not a lot- or batch-level expiry system.
  • The system exposes API endpoints. It does not contain a customer-facing web front end.
Useful presentation honesty: Explain what the code does, not what a full warehouse platform might do. For example, say “the receipt records a bin” rather than “the system maintains bin-level stock balances.”

Request path

Browser / API client ↓ HTTP request FastAPI route → input schema + authentication / role checks ↓ Business logic → SQLAlchemy session → PostgreSQL ↓ Commit only when the operation is valid ↓ JSON response (or a clear HTTP error)

The database session is provided to a request and closed afterward. A write route first checks the request and business rules, then commits. If a database operation fails before commit, the session's uncommitted transaction is rolled back when it closes.

03 · People and access

Roles and permissions

Every normal API action requires a logged-in user except the health check and the documentation pages. The token identifies a user; the application looks up that user on each request and checks the user's current active status and role.

RoleTypical responsibilityExamples of allowed actions
ADMINSet up and maintain users and master data; see administrative reports.Create and deactivate users; manage catalog and warehouses; valuation and movement reports.
WAREHOUSE_MANAGERManage buying and warehouse-level controls for their assigned home warehouse.Create/close/cancel purchase orders; adjust stock; transfer stock; set expiry; see reorder/expiry alerts.
STORE_CLERKRecord receiving and issue operations for their home warehouse.Receive goods against orders; issue stock; read permitted order and stock information.

Scope checks

  • Managers and clerks need an assigned, active home warehouse for warehouse operations.
  • Purchase orders are listed and retrieved only within the user's home warehouse.
  • A clerk receiving goods must use a purchase order and a bin in that same home warehouse.
  • A manager's transfer must start at their home warehouse and go to a different active warehouse.
  • A non-admin can list bins only for their own warehouse.
  • The balance and ledger query endpoints accept any authenticated user and offer warehouse/product filters. They do not apply a home-warehouse-only filter in their route implementation.

Authentication in simple words

  1. The user sends an email and password to POST /auth/login.
  2. The app verifies the password against its Argon2 hash and returns a signed bearer token.
  3. The caller sends that token in the Authorization: Bearer … header.
  4. The API validates the token and reloads the user record. A deactivated user loses access even if their token has not expired.
Presentation tip: A role answers “what kind of action may this user perform?” The home warehouse answers “which warehouse does that action apply to?”
04 · Workflow

End-to-end example: receiving goods

Suppose the warehouse needs 10 boxes of a product. This is the main story to use in a presentation.

  1. Prepare master data. An administrator creates the warehouse, storage bin, supplier, product category, unit of measure, and product.
  2. Create an order. A manager creates a purchase order for a supplier, with one or more product lines and quantities/prices. The order belongs to the manager's home warehouse and starts OPEN.
  3. Receive part of the order. A clerk posts a Goods Received Note (GRN), with the purchase-order line, received quantity, and a bin in the home warehouse.
  4. Update records together. The app increases the PO line's received quantity, creates the GRN and its item, increases the stock balance, and writes a positive RECEIPT ledger entry.
  5. Update the order status. If some amount remains, the order becomes PARTIAL. When every line is fully received, it becomes CLOSED.
  6. Use the stock. A clerk can issue goods against a requisition; a manager can transfer stock or record a physical-count adjustment.
  7. Review. Users can inspect the balance and history; managers see alerts; administrators see reports.
Supplier → Purchase Order → PO lines ↓ GRN + GRN lines ↓ Stock balance + ledger

Purchase-order status meanings

StatusMeaning
OPENCreated and not yet partly received.
PARTIALSome quantity received; at least one line still has outstanding quantity.
CLOSEDMarked finished, either after all quantities arrive or by a manager's close action.
CANCELLEDCancelled before partial receipts; a cancelled order cannot receive goods.

A manager can explicitly close an order even if it has remaining quantities. A partially received order cannot be cancelled; the implementation asks the manager to close it instead, preserving the receipt history.

05 · Workflow

Stock operations

Issue

A clerk records stock leaving the home warehouse, with a product, positive requested quantity, and requisition number. The ledger stores the quantity as a negative number. If the stock would go below zero, the API rejects the operation with 409 Conflict.

Transfer

A manager transfers a positive quantity from their home warehouse to a different active warehouse. The system writes two linked entries: a negative TRANSFER_OUT at the source and a positive TRANSFER_IN at the destination. Both share one generated transfer reference and are committed as one transaction.

Physical-count adjustment

A manager enters the counted quantity and a reason. The app compares that count with the current balance and records only the difference as an ADJUSTMENT. The reason is mandatory. A count equal to the current balance creates no entry; the API responds with a conflict instead of writing a zero movement.

Expiry date

A manager can set or clear the expiry date on a product's warehouse balance. Setting a date is rejected when there is no stock in that position. The date is not separately recorded in the stock ledger.

Example ledger arithmetic

Receive 10 +10 balance 10 Issue 2 -2 balance 8 Transfer out 3 -3 balance 5 Adjustment +1 +1 balance 6 ↑ The ledger's running sum explains the balance.

The balance is the fast “how much now?” answer. The ledger is the “how did we get here?” answer. Each successful movement stores the resulting balance and a sequence number as well as the signed quantity change.

How to describe reports accurately

  • Reorder: strict “below” comparison; stock equal to the reorder level is not listed.
  • Expiry: “EXPIRED” means before today's UTC date. “EXPIRING” includes today and dates through the configured cutoff.
  • Valuation: a current estimate from balances and the product's current unit cost; it is not a historical accounting valuation.
  • Movement: measures issued quantity, not receipts or transfers. Default cutoffs are fast at 20 units or more and slow at 5 or fewer; settings can change these values.

Relationships at a glance

Category ─┐ ├→ Product ← Unit of measure Warehouse → Bin Supplier + Warehouse → Purchase Order → PO Items ↓ GRN → GRN Items → Bin ↓ Stock Balance ↓ changes Stock Ledger User → creates a receipt, issue, transfer, or adjustment

Why store both a balance and a ledger?

  • The balance table makes everyday “how much is on hand?” queries quick.
  • The ledger gives a traceable explanation of each change.
  • Each ledger record's balance_after can be compared with the running sum of changes.
  • The database prevents ledger rows from being updated, deleted, or truncated.

Quantities use decimal numeric columns (three decimal places); money uses numeric columns with two decimal places. This avoids binary floating-point rounding in stock and purchase calculations.

08 · Correctness

How the system keeps stock correct

One controlled movement helper

app/stock.py contains the shared low-level stock logic. It locks the balance row, calculates the new quantity, rejects a negative result, increments the per-position sequence, updates the balance, and stages the matching ledger row. The business route commits after the whole operation is ready.

Concurrency: two requests at the same time

Without a lock, two clerks could both read “1 left,” both issue it, and produce a negative or inconsistent result. The app creates or finds each balance row and locks it for update before changing it. For transfers, it locks source and destination positions in a stable sorted order. Competing requests wait and then see the latest committed values.

Transactions: all of the operation or none

A transfer has two sides. If the outgoing side succeeds but the incoming side fails, committing only half would lose stock. Both sides are part of one database transaction. A failure before commit rolls the operation back so neither side remains.

Duplicate receipt race

Two simultaneous receipts must not both consume the same outstanding PO quantity. The app locks the same purchase-order row before reading and updating its line quantities. The tests verify that only one competing over-limit receipt succeeds.

Database guardrails

  • Unique constraints stop duplicate codes and duplicate position records.
  • Check constraints stop negative balances, invalid PO quantities, invalid roles/statuses, and incorrectly signed movement rows.
  • The ledger trigger rejects UPDATE, DELETE, and TRUNCATE.
  • Indexes support common filters, such as ledger product/time and purchase-order warehouse/status.
Good presentation line: “The app does not just calculate a new stock number. It locks the position, updates the balance, writes the matching audit entry, and commits the complete business operation together.”
09 · Input and security

Validation and HTTP errors

app/schemas.py defines what request and response data should look like. The shared input configuration rejects unknown fields, trims surrounding whitespace on strings by default, and supports returning SQLAlchemy objects through declared response models.

Examples of validation

  • Email fields must be valid email addresses.
  • Passwords for created users must be 12–128 characters; password whitespace is preserved.
  • Quantities and IDs must be positive where required; prices and reorder levels cannot be negative.
  • Decimal fields specify maximum precision and decimal places.
  • Requests cannot include arbitrary extra fields.
  • A purchase order and a GRN must contain at least one line, with no more than 100 lines.
  • Pagination starts at page 1, uses page size 1–100, and validates filter IDs.
  • Date filters reject a start date later than the end date.

Common response codes

CodePlain meaningExample
200Request succeeded.Read or update an existing record.
201New record/operation created.Create an order or post an issue.
204Succeeded with no response body.Archive a product.
401Missing, invalid, expired token or invalid login.Login again with valid credentials.
403Logged-in user lacks the role or warehouse access.A clerk tries to create a purchase order.
404Requested row does not exist in the relevant scope.Unknown product or order outside home warehouse.
409Business rule or database conflict.Insufficient stock or duplicate unique code.

503Health route cannot reach PostgreSQL.Database service is unavailable.

Validation error details report field locations and messages without echoing the submitted values. Database integrity errors are returned as a general conflict message rather than raw database text.

09 · Input and security

Security and configuration

Security controls visible in the code

  • Password storage: Argon2 hashes are stored, not plain-text passwords.
  • Login response: unknown users are checked against a dummy hash as well, helping avoid a simple timing difference between unknown and known users.
  • Signed token: JWT uses HS256 and checks issuer, audience, required claims, and expiration.
  • Deactivation takes effect: every authenticated request reloads the user and checks that the account is active.
  • Least-privilege endpoints: route dependencies enforce roles; business logic also checks warehouse ownership.
  • Browser headers: middleware sets anti-sniffing, frame, and referrer headers; it adds a content policy to docs/static routes and disables caching on API responses.
  • Local docs assets: Swagger UI JavaScript and CSS are served from the repository instead of being loaded from a public CDN.
  • Bootstrap config: setup creates the local .env with restrictive file permissions where supported by the OS.

Configuration keys

Setting familyPurpose

WAREHOUSE_JWT_SECRETPrivate signing secret, at least 32 bytes.
WAREHOUSE_TOKEN_MINUTESAccess-token life; default is 60 minutes.

10 · Reports

Alerts and reporting logic

Reorder alert

For the manager's home warehouse, compare stock quantity with each active product's reorder level. The alert lists rows only when quantity is strictly less than that level. Products without a balance row are treated as having zero stock.

Expiry alert

Look at home-warehouse balance rows with quantity above zero and an expiry date. Dates before today's UTC date are marked EXPIRED. Dates from today through the configured look-ahead cutoff are marked EXPIRING. Rows without an expiry date are not included.

Warehouse valuation

For each warehouse, add up the value of its stock using quantity × product.unit_cost, rounded to two decimal places. The report includes warehouses even when their value is zero. It uses today's unit costs; it does not reconstruct the cost that was current when each movement happened.

Movement analysis

For the requested inclusive date range, total only ISSUE quantities (the route reverses the negative ledger sign to show positive units issued). It classifies totals as FAST, SLOW, or MEDIUM. The thresholds are configurable. Archived products are normally excluded, but a product with an issue during the date range can still appear so that its movement is not hidden.

Limits to keep in mind

  • These are API responses, not visual charts or dashboards.
  • Expiry warnings depend on a date recorded on the aggregate product/warehouse balance, not a batch-level date.
  • Reorder and expiry alerts are warehouse-manager operations and are scoped to that manager's active home warehouse.
  • Valuation and movement analysis require an administrator role.

12 · Quality

How the project is tested

The test suite calls the real FastAPI app and uses PostgreSQL. It creates a new database with a random test-only name, applies the project's migration, and drops that generated database at the end. It does not use the configured application database for test records.

What the tests exercise

  • Health route, Swagger/OpenAPI, static docs assets, and unauthenticated access.
  • Valid, invalid, expired, and inactive-user login behavior; role checks; user creation and deactivation.
  • Master-data creation/update, product search, pagination, and soft archive.
  • PO validation, partial/full receipts, status changes, warehouse scope, and over-receipt rejection.
  • Issue, adjustment, transfer, expiry, balance, ledger, and report calculations.
  • Database-level append-only ledger and nonnegative balance constraints.
  • Concurrency: two requests competing for the last unit and two receipts competing for the same outstanding amount.
  • Atomic rollback: a deliberately failed transfer must leave both warehouse balances and history unchanged.
  • Recomputing running ledger quantities and checking each stored balance/sequence.

Run tests

.\.venv\Scripts\python.exe -m pytest -q

The acceptance documentation also gives an optional coverage command. Tests require a running PostgreSQL server and a login role permitted to create/drop the uniquely named test database.

Do not run tests casually against important data: the fixture targets a generated name and cleans it up, but a working PostgreSQL setup is still required. Follow the README and test configuration.
13 · Run it

How to start the application

The repository README recommends Python 3.11 or 3.12 and PostgreSQL 17. First install Python/PostgreSQL and make sure the database service is running.

Windows PowerShell from the repository folder

py -3.12 -m venv .venv .\.venv\Scripts\python.exe -m pip install -r requirements.txt .\.venv\Scripts\python.exe -m app.setup .\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000

Setup asks for PostgreSQL connection details and an application admin email/password. It writes local settings, creates the database if requested, applies the Alembic migration, and creates the first admin user. The database password and the application's login password are two different credentials.

Open Swagger

With the server running, open http://127.0.0.1:8000/docs. Select Authorize and log in using the admin email and application password. Use Authorize → Logout to switch roles for a demo.

Useful setup concepts

  • Migration: applies the versioned schema to the selected database.
  • Bootstrap admin: creates the first account allowed to manage users and catalog records.
  • Database server password: lets the app connect to PostgreSQL; it does not log the user into the API.
  • Application password: used at the API login screen; stored as an Argon2 hash.
  • JWT secret: signs login tokens; it must stay private and stable while tokens are in use.

15 · Review

Questions you may be asked

Why have both a balance table and a ledger?

The balance gives a quick current answer. The ledger gives the explainable history. Keeping both avoids recalculating every current quantity from all old movements on every read, while still keeping a movement trail.

How do you stop negative stock?

The app locks the position, checks the result before saving, and the database also has a nonnegative constraint. Competing operations wait for the lock and then see the latest balance.

How do you avoid a half-completed transfer?

Both stock legs are part of one transaction. If either fails, neither is committed. A test intentionally forces a failure after the first leg and verifies rollback.

Why does the user have a warehouse?

It scopes manager and clerk operations. Orders, receipts, and transfers are checked against the user's active home warehouse.

Can you delete a product?

The API archives it by setting a flag instead of physically deleting it. This keeps references and history intact. Archived products are excluded from normal product search.

Is the expiry date tracked for every lot?

No. The expiry date is stored on the overall product/warehouse balance row. Lot-level quantities and dates are not modeled in this version.

Does this include a dashboard?

No separate dashboard is in this repository. Swagger UI is the included web page for trying the REST API.

How do you know the behavior works?

Automated tests call the API against a fresh PostgreSQL test database and check business rules, role failures, concurrency, rollback, and database constraints.

What is an area for future improvement?

Possible extensions—if requirements call for them—include lot/batch-level stock and expiry, bin-level balances, a dedicated front end, richer audit/reporting, and integration with external systems. These are ideas, not current features.

30-second presentation summary

“This project is a warehouse inventory REST API built with FastAPI, SQLAlchemy, and PostgreSQL. It manages catalog data, purchase orders, receipts, and stock movements. It separates access into administrator, warehouse manager, and store clerk roles. For stock changes, it keeps a current balance and an append-only ledger, and it uses database transactions and row locks to prevent inconsistent concurrent updates. Swagger UI makes the API easy to demonstrate, and PostgreSQL-backed tests cover business rules, access control, and failure cases.”
